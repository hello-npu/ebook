# 08. vLLM 이해하기

> 담당(오너): ⬜  ·  관련 세미나 주차: W11  ·  상태: 초안

## 개요

vLLM은 LLM(대규모 언어 모델) 추론·서빙을 빠르고 효율적으로 하기 위한 엔진입니다. 이 장에서는 LLM 서빙이 왜 어려운지, vLLM이 어떤 아이디어로 그 문제를 푸는지를 정리합니다. NPU에서 LLM을 서빙([9장](09-llm-serving.md))하고 문제점을 개선([10장](10-serving-improve.md))하기 위한 기초가 됩니다.

## 배경 / 이론

### LLM 추론은 왜 어려운가

LLM은 토큰을 하나씩 순차적으로 생성합니다(autoregressive). 이때 두 단계가 있습니다.

- 프리필(prefill): 입력 프롬프트 전체를 한 번에 처리하는 단계
- 디코드(decode): 토큰을 한 개씩 이어서 생성하는 단계

디코드 단계에서는 이전까지 계산한 키·값(KV)을 다시 쓰기 위해 메모리에 저장하는데, 이를 KV 캐시라고 합니다. 시퀀스가 길어지고 동시 요청이 많아질수록 KV 캐시가 메모리를 크게 차지합니다. 결국 LLM 서빙의 병목은 연산보다 메모리(특히 KV 캐시) 관리인 경우가 많습니다.

### PagedAttention

전통적인 방식은 각 요청에 KV 캐시 공간을 연속된 큰 덩어리로 미리 잡습니다. 그러면 실제로 다 쓰지 않는 공간이 낭비되고(내부 단편화), 길이를 예측하기 어려워 메모리를 비효율적으로 씁니다.

vLLM의 PagedAttention은 운영체제의 가상 메모리 페이징처럼, KV 캐시를 작은 블록(page) 단위로 나눠 필요할 때마다 할당합니다. 덕분에 단편화가 줄고, 같은 메모리로 더 많은 요청을 동시에 처리할 수 있습니다.

### Continuous Batching

여러 요청을 묶어 한 번에 처리하면(batching) 하드웨어 활용도가 올라갑니다. 하지만 요청마다 생성 길이가 다르므로, 고정 배치로 묶으면 먼저 끝난 요청이 다른 요청을 기다리며 자원을 놀립니다.

vLLM은 토큰 생성 단위로 배치를 동적으로 재구성합니다(continuous batching). 끝난 요청은 빠지고 새 요청이 즉시 합류해, 처리량을 크게 끌어올립니다.

### 처리량 vs 지연 시간

서빙 성능은 보통 두 축으로 봅니다.

- 지연 시간(latency): 한 요청이 끝나기까지의 시간. 사용자 체감 속도.
- 처리량(throughput): 단위 시간당 처리한 토큰/요청 수. 서버 효율.

배치를 키우면 처리량은 오르지만 개별 지연이 늘 수 있습니다. 둘은 트레이드오프 관계이며, 서빙 튜닝은 이 균형을 맞추는 일입니다. 이 트레이드오프를 NPU 환경에서 직접 측정하는 것이 [10장](10-serving-improve.md)의 핵심입니다.

## NPU 서빙에서 왜 중요한가

vLLM은 본래 GPU를 겨냥해 발전했지만, 핵심 아이디어(PagedAttention, continuous batching)는 하드웨어와 독립적인 개념입니다. NPU에서 vLLM을 쓰려면 NPU 백엔드(예: vllm-rbln)를 통해야 하며, 메모리 구조·지원 모델·파라미터가 GPU와 다를 수 있습니다. 우리가 풀려는 문제는 바로 이 지점 — "NPU + vLLM 조합에서 무엇이 잘 되고 무엇이 병목인가" — 입니다.

> 📝 실습 채움: 우리가 쓰는 vLLM/NPU 백엔드 버전과 지원 모델 목록을 확인해 정리합니다.

## 정리

- LLM 서빙의 병목은 흔히 KV 캐시 메모리 관리에 있습니다.
- vLLM은 PagedAttention으로 메모리 단편화를, continuous batching으로 배치 비효율을 해결합니다.
- 처리량과 지연은 트레이드오프이며, 서빙 튜닝의 핵심입니다.
